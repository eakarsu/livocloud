# LivoCloud

LivoCloud is a Spring MVC WAR backed by PostgreSQL. The implemented, supported
journey is account registration and email verification:

1. A prospective customer submits a name and email address.
2. The application persists one normalized account and binds it to the session.
3. The customer supplies a company and password; the password is stored as a
   salted PBKDF2-SHA256 hash and a 24-hour verification capability is issued.
4. Mail delivery either succeeds or produces an explicit retry state. Retrying
   invalidates the previous capability.
5. The verification link atomically changes the account state and consumes the
   capability. Replays and expired links fail without changing the account.
6. After accepting the terms, an active customer can sign in. Successful login
   rotates the HTTP session identifier.

The cloud-instance and payment paths are deliberately fail-closed with HTTP 501;
they are not part of this bounded completeness increment.

## Requirements

- JDK 11 or newer (the generated bytecode remains Java 8 compatible)
- Maven 3.9+
- PostgreSQL 14+

Create a database and export the variables documented in [.env.example](.env.example).
The application runs versioned Flyway migrations at startup. Never place real
credentials in `.env.example` or another tracked file.

```sh
mvn clean verify
mvn package
```

Deploy `target/livocloud-0.0.1-SNAPSHOT.war` to a Servlet 3.1-compatible
container. For a reproducible local topology, set `LIVOCLOUD_DB_PASSWORD` and run:

```sh
docker compose up --build
```

The service is then available at `http://localhost:8080/LivoCloud/`; readiness is
reported by `GET /LivoCloud/health` (HTTP 200 only when the database responds).

## Configuration

| Variable | Required | Purpose |
| --- | --- | --- |
| `LIVOCLOUD_DB_DRIVER` | no | JDBC driver; defaults to PostgreSQL |
| `LIVOCLOUD_DB_URL` | production | PostgreSQL JDBC URL |
| `LIVOCLOUD_DB_USERNAME` | production | Least-privileged application role |
| `LIVOCLOUD_DB_PASSWORD` | production | Application database credential |
| `LIVOCLOUD_PUBLIC_BASE_URL` | production | Public HTTPS base used in verification links |
| `LIVOCLOUD_MAILGUN_API_KEY` | for mail | Mailgun credential |
| `LIVOCLOUD_MAILGUN_API_URL` | for mail | Account-specific Mailgun messages endpoint |
| `LIVOCLOUD_MAIL_FROM` | for mail | Verified sender identity |

Missing mail configuration does not roll back saved registration data. The UI
reports delivery failure and allows an authenticated retry. Missing database
configuration or a failed migration prevents application startup.

## Security and operations

- Every state-changing MVC request requires a session CSRF token.
- Registration attempts are limited per normalized email and client address in a
  shared database-backed 15-minute window; only one-way digests are retained.
- Registration/profile/resend operations use the server-side session user ID,
  not a submitted email address, as their authority boundary.
- Verification tokens are random 256-bit capabilities; only SHA-256 digests are
  stored. Passwords use 210,000-round PBKDF2-SHA256 with per-password salts.
- `account_audit` records registration, issuance, resend, and verification events.
- Provider responses and raw capabilities are not logged.

The original repository contained live-looking AWS, Mailgun, PayPal, and demo API
credentials. They have been removed from the working tree, but remain in Git
history. Revoke/rotate them immediately before deployment and coordinate any
history rewrite with all repository users. Their exact original-commit
fingerprints are baselined in `.gitleaksignore` so CI rejects new findings without
pretending the historical exposure is fixed. Existing plaintext-password rows are intentionally rejected;
use a verified password-reset/migration process rather than silently accepting
legacy plaintext.

Backup, restore, failure recovery, and deployment checks are described in
[docs/OPERATIONS.md](docs/OPERATIONS.md).
